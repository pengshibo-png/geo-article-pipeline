## 1. 为什么要立这份表

原系统的变量定义**散落在三处**，且互相不一致：

| 位置 | 问题 |
|---|---|
| 各段 Prompt 正文 | 实际使用的变量 |
| 施工规格书 §6.1 | 登记的变量——**`{genre_mix}` 在用但漏登记**；**`{cities}`、`{image_html}` 登记了但从未使用** |
| 各段变更说明 | 修复过程中新增的变量，无处归档 |

结果就是**没人能说清"到底有几个变量"**——这正是缺陷 D1/D2/D3 能长期存在的土壤。

**立这份表的直接目的**：把"变量"从三个地方收敛到一处，并**用脚本证明四段 Prompt 与本表一致**（见 §5）。

## 3. 两个「派生/渲染型」变量（各有唯一来源文件）

这两个变量**不是直传值，而是由系统渲染**——因为它们曾经是跨段矛盾的源头。

| 变量 | 唯一来源 | 渲染依据 |
|---|---|---|
| `{contact_rule}` | **`_共享/contact-rule.md`** | `contact_mode` ∈ {keep, revise, strip}，缺省 `revise` |
| `{brand_names}` | **`_共享/brand-names.md`** | 从品牌资料的「品牌概述」+「资质与认证」分区派生 |

**使用铁律**：三段 Prompt **只引用不复制**。修改规则 = 只改这两个文件，各段自动生效。

其余渲染型变量（不涉及跨段一致性，风险低）：
`{city_rule}`（系统计算）、`{angle}`（A 段附录视角表）、`{current_period}`（服务器时间，时区 `Asia/Shanghai`）。

## 5. 一致性校验（**可执行，替代人工核对**）

`_共享/check_variables.py` 做了四件事：

| # | 校验 | 目的 |
|---|---|---|
| V1 | 四段 Prompt 里出现的变量 **⊆ 本表** | 防止出现未登记的"野变量" |
| V2 | 本表中属于该段的**必填**变量 **⊆ Prompt 实际使用** | 防止漏注入 |
| V3 | 各段变量数量与本表登记数一致 | 防止统计口径漂移 |
| V4 | 扫描硬编码（电话 / 年份 / 品牌名 / 行业词） | 门禁 G3，含**新增的品牌名一类** |

**运行**：

```bash
python _共享/check_variables.py          # 全量校验
```

**退出码 0 = 全部通过，非 0 = 存在问题**（可直接接入 CI）。

---

## 6. 变更纪律

1. 新增变量 → 先改 `variable-registry.json` + 本表，再改 Prompt；
2. 变量改名 → 四段 + 两个共享文件**一次性改完**，跑一次 `check_variables.py`；
3. 任何"这段 Prompt 里临时加个变量"的做法**一律不允许**——那正是原系统把变量搞乱的路径。
